# 邮箱发信配额问题（上线后发现）

- **状态**：发信通道已迁出个人邮箱（2026-09-20），治标限流项仍待做
- **记录时间**：2026-09-11
- **优先级**：中（影响新用户注册，但当前量级未触发）

## 背景

上线后部分用户注册收不到验证码。已定位为**发信通道（QQ 个人邮箱）的账号级配额/风控限制**，不是代码缺陷，也不是网络或 SMTP 配置问题。

## 已查清的结论

- **收不到 + 前端弹 500**：QQ 只实时校验自家域名，收件人为不存在的 QQ 邮箱时在 RCPT 阶段直接拒收（`550 The recipient may contain a non-existent account`），异常冒泡被兜底处理器转成 500。**已修复**：`VerifyCodeService` 捕获 `MailException` 并翻译为可读提示。
- **收不到但接口返回 200**：非 QQ 域名收件人 QQ 不做校验，先接收后投递失败或进垃圾箱，用户侧毫无提示——排查时注意区分这两种表现。
- **QQ 官方说明**：限制为**账号级阶梯式动态保护**（超每分钟禁几分钟／超每小时禁几小时／超每日当日禁发），**与发信 IP、发信域名无关**（换服务器、换 IP 都无效），具体数值不公开，信誉恢复需长期合规发信积累。
- 社区实测量级约每天 100~500 封（各来源数值不一致，仅供参考）。

参考资料：
- [退信提示：550 Sender frequency limited - QQ邮箱帮助中心](https://help.mail.qq.com/detail/0/1071)
- [邮件推送 计费方式 - 阿里云帮助中心](https://help.aliyun.com/zh/direct-mail/billing-methods)

## 发信通道迁移（2026-09-20，已完成）

原计划迁阿里云 DirectMail（理由：支持 SMTP、业务代码无需改）。实际改选**腾讯云邮件推送 SES**，
因为自有域名 `dsxnb.com` 的发信地址已建在腾讯云侧。落地方式与原计划不同，两个约束值得记下来：

- **不能走 SMTP**：腾讯云自 2026-03-02 起，新开通 SES 的**个人实名用户不再支持 SMTP 协议发信**
  （企业实名不受影响）。本次账号正受此限制，故改为调用 **SendEmail API**。
- **API 默认只支持模板发信**（`Simple` 直传正文已废弃），模板需在控制台提交审核（约 1 个工作日）；
  且「普通发送」所用的模板**只支持单一变量**，因此模板正文里只放了 `{{code}}`，有效期文案写死在模板中
  —— 改动 `eggworld.mail.code-expire-minutes` 时必须同步改控制台模板正文。

配套改动：

- 发信实现改调 `tencentcloud-sdk-java-ses`，云 API 错误码翻译为可读业务提示（`VerifyCodeService.toBusinessException`）
- 发信参数（发信地址、SecretId/SecretKey、模板 ID）走 `application-prod.yml` 的 `eggworld.mail.*`，
  与数据库口令一样**不入库**；未配置时降级为「验证码打印日志」，本地开发流程不受影响
- 已移除 `spring-boot-starter-mail` 依赖与 `spring.mail.*` 配置

本地实测（2026-09-20）：真实邮箱发送成功；**向不存在的收件人发信同样返回 200** —— SES 异步投递、不做实时收件人校验。
也就是说 QQ 时代那种「收件人不存在 → 550 → 前端弹 500」不会再出现，取而代之的是**静默失败**（接口 200 但收不到信），
排查时要先看后端日志有没有 `[DEV] 未配置腾讯云 SES 发信参数` 与 `TencentCloudSDKException`。这也让下面的待办①更重要。
