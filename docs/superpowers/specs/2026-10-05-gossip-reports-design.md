# 八卦大厅爆料区设计

日期：2026-10-05  
状态：已获需求确认，待进入实现计划（含全站公告）
实现分支：`codex/gossip-reports`

## 1. 目标与边界

在现有八卦大厅中增加独立的「爆料区」Tab，让用户发布校园吐槽或爆料。普通用户的内容先由管理员审核，审核通过时由管理员决定平台奖励金额；管理员发布的内容可以直接公开，但奖励必须由另一位管理员决定，避免发布者给自己发奖励。

第一版明确不支持爆料图片、不做爆料分类、不改变现有「打听」模块的冻结悬赏、回答、采纳和退款逻辑。

## 2. 用户规则

### 2.1 发布

- 表单字段：标题、正文、实名/匿名。
- 标题与正文必填；沿用项目现有文本长度校验策略。
- 普通用户发布后进入 `pending`，前台不可见，管理员审核台可见。
- 主管理员或副管理员发布后直接进入 `published`，不进入内容审核。
- 匿名只影响前台展示；后台审核、奖励和审计仍保留真实发布者。
- 标题、正文提交前调用现有敏感词库进行拦截；命中时不提交、不落库，并提示用户修改。

### 2.2 审核与奖励

- 普通用户爆料：管理员审核通过时填写奖励金额，允许为 0；通过与奖励结算在同一事务内完成。
- 审核驳回不发放奖励，并保存处理原因。
- 管理员爆料：内容立即公开，奖励状态为“待定”；另一位管理员设置奖励金额并结算，允许为 0。
- 奖励由平台直接发放，统一通过 `PointService` 写入用户余额和 `point_logs`。
- 每条爆料最多结算一次；奖励结算使用独立奖励记录的唯一 `report_id` 防止并发重复发币。
- 奖励决定人不能是该条爆料的发布者；普通用户爆料不受此限制。

### 2.3 互动与治理

- 已公开爆料支持文字评论和点赞。
- 评论不支持图片。
- 评论提交前同样执行敏感词拦截；后端再次校验，不能只依赖前端。
- 管理员可以隐藏或删除已公开爆料，也可以隐藏或删除评论，并记录操作人和原因。
- 隐藏/删除后的内容不出现在公开列表；管理员后台仍可查到处理记录。

## 3. 推荐架构

采用独立爆料模块，不扩展 `gossip_posts`，原因是现有 `gossip_posts` 的金币来自发布者冻结悬赏，而爆料金币来自平台发放；混用会导致状态、退款和审计逻辑互相污染。

### 3.1 数据表

新增迁移文件 `backend/sql/migrate-gossip-reports.sql`，不执行 `init.sql`。

#### `gossip_reports`

- `id`：主键
- `title`、`content`：标题和正文
- `publisher_id`：发布者，保留用户 ID，不加会阻止用户物理删除的外键
- `anonymous`：是否匿名展示
- `status`：`pending`、`published`、`rejected`、`hidden`、`deleted`
- `reward_amount`：平台奖励，非负整数，默认 0
- `reward_status`：`pending`、`settled`、`none`
- `reviewer_id`、`review_reason`、`reviewed_at`：审核/处理信息
- `created_at`、`updated_at`
- 索引：`status + created_at`、`publisher_id + created_at`

#### `gossip_report_comments`

- `id`、`report_id`、`author_id`、`content`
- `status`：`visible`、`hidden`、`deleted`
- `moderator_id`、`moderation_reason`、`moderated_at`
- `created_at`
- 索引：`report_id + status + created_at`

#### `gossip_report_likes`

- `id`、`report_id`、`user_id`、`created_at`
- 唯一键：`report_id + user_id`，防重复点赞

#### `gossip_report_rewards`

- `id`、`report_id`、`recipient_id`、`amount`、`operator_id`
- `created_at`
- `report_id` 唯一，作为奖励结算幂等闸门；金额为 0 也落一条结算记录，表示已决定、不再重复发放

### 3.2 后端接口

公开/登录读取：

- `GET /api/gossip/reports?page=&size=`：只返回 `published` 内容
- `GET /api/gossip/reports/{id}`：公开详情与可见评论
- `GET /api/gossip/reports/{id}/comments`：可见评论分页

登录写入：

- `POST /api/gossip/reports`：发布爆料
- `POST /api/gossip/reports/{id}/comments`：发表评论
- `POST /api/gossip/reports/{id}/like`：爆料点赞

管理员/副管理员审核与治理：

- `GET /api/admin/gossip-reports/pending`：待审核与待定奖励列表
- `POST /api/admin/gossip-reports/{id}/approve`：普通用户爆料审核通过并设置奖励
- `POST /api/admin/gossip-reports/{id}/reject`：驳回并记录原因
- `POST /api/admin/gossip-reports/{id}/settle-reward`：为管理员发布的爆料设置奖励；校验操作人不能是发布者
- `POST /api/admin/gossip-reports/{id}/hide`、`/delete`：治理爆料
- `POST /api/admin/gossip-report-comments/{id}/hide`、`/delete`：治理评论

所有写入接口都使用服务端身份和数据库状态判断，不信任前端传入的发布者、审核人、奖励状态或金币流水状态。


## 3.3 全站公告模块

公告与爆料模块一并实现，但使用独立的 `announcements` 表和独立权限，不混入爆料状态。

- 字段：标题、正文、发布人、状态、发布时间、创建时间、更新时间。
- 公告只支持文字，不支持图片、评论、点赞或用户编辑。
- `GET /api/announcements` 允许匿名读取，返回已发布公告，支持最新公告和历史列表。
- 主管理员专属接口：发布、编辑、下架；接口使用 `@AdminOnly`，副管理员和普通用户均返回 403。
- 主管理员点击发布后立即生效，无定时发布功能。
- 前台在全站公共壳层显示最新公告入口/提示，未登录访客也可看到；公告详情显示发布人昵称。
- 公告下架后不出现在公开列表，主管理员仍可在后台查看历史记录。
- 发布、编辑、下架都记录操作人和操作时间；不允许把前端传入的发布人当作权限依据。

公告验收重点：匿名读取、发布人展示、立即发布、主管理员可写、副管理员/普通用户只读、下架后不可公开读取。
## 4. 前端设计

- 在现有 `#page-gossip` 内增加一级 Tab：`打听` / `爆料区`；默认保持现有打听页，避免改变老用户入口。
- 爆料区复用现有八卦卡片视觉，不复用打听卡片中的悬赏/采纳文案。
- 卡片显示：标题、正文摘要、发布时间、实名昵称或“匿名爆料”、奖励状态、评论数、点赞数。
- 发布面板显示标题、正文和实名/匿名开关；不显示图片上传控件。
- 审核失败、敏感词命中、重复点击、未登录、网络失败均给出明确提示，失败不清空草稿。
- 评论输入框只允许文字，提交按钮有独立提交锁，敏感词命中时保留草稿。
- 管理员工作台增加“爆料审核”区域，显示待审内容、实名发布者、正文、评论、奖励输入和处理原因。
- 全站公共壳层增加公告入口/最新公告提示；公告卡片显示标题、正文摘要、发布人和发布时间，未登录也可读取。
- 仅主管理员显示公告发布、编辑、下架操作；副管理员和普通用户不显示写操作。

## 5. 数据流与一致性

### 普通用户爆料

`POST` 校验登录/字段/敏感词 → 写入 `pending` → 管理员审核 → 事务内条件更新为 `published`、写入审核信息 → 插入唯一奖励记录 → 奖励大于 0 时调用 `PointService` → 奖励状态置 `settled` → 通知发布者。

### 管理员爆料

管理员发布 → 服务端判断 `isModerator` → 直接写入 `published + reward_status=pending` → 另一管理员审核奖励 → 条件更新奖励状态并插入唯一奖励记录 → 奖励大于 0 时调用 `PointService`。

所有审核、奖励、隐藏、删除操作都使用“当前状态必须匹配”的条件更新；影响行数为 0 时返回“内容已被其他管理员处理”，不能重复执行。

## 6. 敏感词与安全

- 复用现有 `chat_sensitive_words` 数据和后台维护入口；只使用启用词。
- 前端可以提前提示，后端必须再次校验标题、正文、评论。
- HTML 渲染统一使用现有转义策略，不把用户内容作为 HTML 直接执行。
- 匿名只在 VO 层隐藏昵称，管理员 VO 返回真实发布者。
- 奖励金额限制为非负整数，并设置单次上限配置，防止误填超大金额；上限值在实现前沿用项目现有金币接口约束并写入测试。
- 不记录密码、Token 或生产连接信息。

## 7. 测试与验收

后端：

- 普通用户发布进入待审核；管理员通过/驳回状态正确。
- 管理员发布直接公开，另一管理员可结算奖励，发布者本人不能结算自己的奖励。
- 奖励 0、正数、负数、非整数和超上限校验正确。
- 并发审核/并发结算只能产生一次奖励记录和一次金币流水。
- 敏感词在标题、正文、评论命中时均被后端拦截。
- 匿名/实名展示权限正确；隐藏、删除后公开接口不可见。
- 评论点赞唯一性、未登录权限和已删除内容边界正确。

前端：

- 八卦大厅 Tab 切换、列表、详情、发布、评论和点赞流程。
- 提交失败保留草稿，重复点击只产生一个请求。
- 移动端与桌面端无横向溢出；管理员审核台可操作奖励和原因。
