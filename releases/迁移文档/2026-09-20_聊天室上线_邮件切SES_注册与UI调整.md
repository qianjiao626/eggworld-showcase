## 三、数据库变更

**脚本（两个，都要执行）**

| 脚本 | 内容 | 影响 |
|---|---|---|
| `backend/sql/migrate-chatroom.sql` | **15 张表**：`chat_conversations`、`chat_conversation_members`、`chat_messages`、`chat_messages_archive`、`chat_read_states`、`chat_friend_requests`、`chat_friends`、`chat_follows`、`chat_blocks`、`chat_groups`、`chat_group_members`、`chat_mutes`、`chat_reports`、`chat_sensitive_words`、`chat_audit_logs` | 纯 `CREATE TABLE`（含 `IF NOT EXISTS`），不改存量数据 |

两个脚本**均不含** `DROP` / `TRUNCATE` / `ALTER` 语句，也不含 `USE` / `CREATE DATABASE`（已逐行核对；脚本开头注释亦声明）。其中 3 处 `ON DELETE CASCADE` 是外键定义（`chat_conversation_members`、`chat_read_states`、`chat_mutes` 的 `conversation_id` → `chat_conversations.id`），**只在删除会话时级联**，本次迁移不会触发。

**库备份命令（执行迁移前；库 dump 统一放 `backup/db/` 这一层）**

```bash
mysqldump -u eggworld -p eggworld > ~/eggworld/backup/db/eggworld_$(date +%Y%m%d_%H%M%S).sql
chmod 600 ~/eggworld/backup/db/*.sql
ls -l ~/eggworld/backup/db/ | tail -3          # 属主 xiaos、大小非 0
head -1 ~/eggworld/backup/db/<本次 dump>        # 能读出内容才算有效备份，读不回来就暂停发布
```

**3. ⚠️ nginx 新增 `/ws/` 反代（必须；线上配置变更，需单独授权）**

**现网实测（2026-09-21 抄录线上 `/etc/nginx/conf.d/dsxnb.conf`）：确认没有 `/ws/` location。** 该文件共 4 个 server 块：前 3 个是 `www.dsxnb.com` / `http` → `https://dsxnb.com` 的 301；第 4 个是本站的 `listen 443 ssl;`（**无 http2**）+ `server_name dsxnb.com;`，块内依次是 `location = /MKJ` 与 `^~ /MKJ/`、`/dd/api/`、`/dd/health`、`/dd/blind-box/`、`/dd/`、`location /api/`（→ `127.0.0.1:8090`）、`location /xs/`（→ `localhost:3000`，原根路径 Node 项目）、`location /`（`root /home/xiaos/eggworld/xs`）、`location = /index.html`（`expires -1`）。**没有 `/ws/`，也没有 `/api/auth/` 限流 location**（后两点与仓库副本 `backend/deploy/dsxnb.conf` 不同，见下）。

因此现状是：前端请求 `/ws/chat` 会落到 `location /` 被当静态路径处理（`try_files` 兜到 `index.html`），SockJS 握手必然失败 —— **不加上这一段，聊天室在线上只能看历史消息，不能实时收发**。

上线前再确认一次（以实测为准）：

```bash

sudo grep -rn "location .*ws" /etc/nginx/conf.d/ /etc/nginx/sites-enabled/ 2>/dev/null
```

未配置时，**在 `listen 443 ssl; server_name dsxnb.com;` 那个 server 块内**（`location /api/` 之后、`location /xs/` 之前最好找）插入下面这段。前缀匹配下 `location /ws/` 比 `location /` 更具体，会正确命中，**不需要**加 `^~`：

```nginx
    # 聊天室 WebSocket（SockJS + STOMP）：必须带 Upgrade/Connection，并放宽长连接超时
    location /ws/ {
        proxy_pass http://127.0.0.1:8090/ws/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 3600s;      # 长连接，别用默认 60s
        proxy_send_timeout 3600s;
    }
```

```bash
curl -s https://dsxnb.com/ws/chat/info            # 期望 200 且返回 JSON（含 "websocket":true）
```

**⚠️ 禁止用仓库副本整文件覆盖线上 conf。** 仓库里的 `backend/deploy/dsxnb.conf` **不等于现网**——它比现网多出**从未在线上生效过**的内容：文件顶部 `limit_req_zone` + `location /api/auth/` 限流、`listen 443 ssl http2`、HSTS / X-Frame-Options / X-Content-Type-Options / Referrer-Policy / Permissions-Policy / CSP-Report-Only 等响应头，以及 `location ~ /\.`、危险后缀 deny 等规则。整文件覆盖会把它们一起带上线（超出本次范围，且 `/api/auth/` 限流会影响登录/验证码）——**本次只做「插入 `/ws/` 一段」这个最小改动**；回滚也只用第 1 步备份的**现网 conf**。

- `/api/` 的 location **不需要**为 WebSocket 加 Upgrade——聊天室走的是独立的 `/ws/` 前缀（现网只有 `/api/` 一个转发 location）
- 未做本步的典型症状：聊天室页面能打开、历史消息能加载（HTTP 接口正常），但**新消息不实时出现**，浏览器控制台报 SockJS 握手失败或「收到 HTML」（`try_files` 兜到了 `index.html`）
