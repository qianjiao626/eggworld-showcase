## 一、本次范围

修复 2026-09-25 线上事故：**在审核中心点任务审核卡，会被宿舍图片审核的点击代理截获**，请求打到 `POST /api/dormitories/review/null` → 500「服务器内部错误」，而任务审核的驳回请求根本没发出去。

根因（已用线上日志与生产库坐实）：

- `js/dormitory.js` 用全局 click 代理宿舍审核按钮，选择器是 `closest('[data-review]')`；
- `growth-schoolv3.html` 的任务审核卡恰好也写了**布尔属性** `data-review`（且没有 `data-id`）；
- 于是在审核中心**点卡片任意位置（含卡内「通过」「驳回」按钮，事件冒泡）**都会被宿舍模块截获：`getAttribute('data-id')` → `null` → 拼出 `/api/dormitories/review/null`；同时 `getAttribute('data-review')` 对布尔属性返回 `""`，不等于 `'approve'` → 走宿舍「驳回」分支，**弹出浏览器原生的「驳回原因（可留空）」输入框**（这正是被误认成"我在驳回任务"的原因）。

本次改动三块：

1. **宿舍模块选择器收紧 + 空 ID 守卫**：`closest('[data-review]')` → `closest('[data-review][data-id]')`，并在取不到 ID 时不发请求（不再可能拼出 `null`）；
2. **消除同名冲突**：任务审核卡改用专属属性 `data-review-card`，同步 `approve()/reject()` 里的 `closest` 选择器；
3. **审核通过加二次确认**：审核中心「通过」改为先弹确认框（「通过」与「通过修改」两条路径共用）——通过后任务**立即上线到任务大厅**，且与相邻的「驳回」误触代价高，确认框里写明这一后果。

事故当晚（2026-09-25 22:06）的完整证据链，仅作背景记录、不在本次改动范围内：

- `22:06:14 POST /api/admin/tasks/151/approve → 200`（任务 151 上线，库内通知「已审核通过，经验值 +5」）；
- `22:06:18 POST /api/dormitories/review/null → 500`（`MethodArgumentTypeMismatchException: For input string: "null"`）；
- 该时间段 nginx **无任何 `/reject` 请求** → 驳回从未生效。
