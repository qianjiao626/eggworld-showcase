## 一、本次范围

**用户反馈**：组队任务人还没满，就从广场上找不到了。

**根因**：`DeadlineScheduler.expire()` 在报名截止到期时，以「有无**入选**（`memberCount`）」为判据：

```java
long members = taskService.memberCount(task.getId());
if (members > 0) { ... 按现有人数开工 ... }
// 无人入选（哪怕有人报名）→ 解散下架     ← 旧逻辑
if (taskMapper.expireIfApproved(task.getId()) == 0) return false;
```

但组队任务的报名只是**候选池**，必须发布者「选人」才算入选。于是出现：

- 有 3 人报名、名额 3 人，但发布者还没来得及选人
- 报名截止一到 → `members == 0` → 任务被置 `expired` 并退币 → **从广场消失**

**修复（方案 A：组队 = 长期招募）**：组队型**取消报名截止**，只要没满员就一直挂在广场、一直可报名；
只有两条路径能让组队离开招募 ——「满员转 `full`」与「90 天兜底」。

```java
// ① 唯一口径函数：组队永远没有报名截止（早于「填了就用它」判断，忽略库里残留的显式截止）
public static LocalDateTime effectiveSignupDeadline(Task task) {
    if (task == null) return null;
    if ("team".equals(task.getTaskType())) return null;   // 组队：长期招募，无报名截止
    if (task.getSignupDeadline() != null) return task.getSignupDeadline();
    ...
}

// ② DeadlineScheduler 主循环必须先分流组队（否则 deadline==null 会被「长期有效」分支 continue 跳过，
//    90 天兜底形同虚设）—— 这是本次最容易漏的一点
if ("team".equals(task.getTaskType())) { if (expireTeam(task)) expired++; continue; }

// ③ 兜底时钟锚定 max(created_at, updated_at)：
//    tasks.created_at 没有 ON UPDATE、renewIfExpired 只改 signup_deadline，
//    若按 createdAt 算，重新发布后会立刻被二次下架并白退一次币
private boolean expireTeam(Task task) {
    LocalDateTime since = max(task.getCreatedAt(), task.getUpdatedAt());
    if (since.plusDays(TEAM_RECRUIT_FALLBACK_DAYS).isAfter(now)) return false;
    // 下架 + 退 10 + 通知可重新发布
}
```

**为什么不是「候选池有人就不下架」**：那只修掉了「找不到」，没修「凑不满人」——
任务虽留在广场，报名入口仍被 `ClaimService` 的截止校验拦住，用户看到的是「看得见、点不动」。
方案 A 让报名入口与展示口径一起放开，才真正解决用户诉求。

**配套改动**：

- `RefundScheduler` 的「3 天无人认领自动退回」把组队型移出（只保留求助型）——
  该任务统计的是「报名数」，与组队「长期招募」语义冲突；组队收口统一交给 90 天兜底。
- `ClaimService`：规则收敛到 `effectiveSignupDeadline` 一处，**不再自己写 `team` 例外**
  （避免三处重复判断导致漂移，正是代码注释里警告的「看得见拦不住」）。
- 移除已无调用点的 `DeadlineScheduler.hasCandidates()`（组队不再依赖候选池判据）。

**前端同步（`growth-schoolv3.html`）**：前端有一份同口径的旧逻辑，必须一起改，否则会出现
「前端判死、后端还留着」的错位：

- `signupDeadlineOf()`（后端口径的镜像）：**组队直接返回空**，且判断早于「填了就用它」，
  与后端 `effectiveSignupDeadline` 逐条对齐
- `scanAndRefundExpiredTasks()`：扫描列表由 `['helpUserList', 'teamUserList']` 收窄为 `['helpUserList']`，
  类型过滤改为只放行 `help`；删除 `taskType === 'team'` 的退款分支（原先固定退 10）
- 任务详情弹窗的自动退回倒计时：条件由 `(taskType === 'help' || taskType === 'team')` 收窄为只对 `help`
- 卡片右下角与详情「报名截止」行：组队不再显示「长期有效」（那是奖励型文案），
  改为 **「招募中」/「招募中（长期，招满即止）」**
- 「我的信息」页蛋蛋币「消耗途径」文案：`组队/求助 3 天无人响应自动退回` → `求助 3 天无人认领自动退回（组队改为长期招募）`

> ⚠️ 如实说明：该前端扫描逻辑在 v3 中**实际是死代码** —— `data-created-at` 属性在
> `buildApiTaskCard()` 里从未输出（全站无写入点），因此它此前并不会真的改动任何任务状态。
> 本次改动属于**口径与文案一致性修复**，不是行为修复；组队任务此前消失的真实原因在后端。
