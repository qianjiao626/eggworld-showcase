## 二、标准上线流程

> **铁律：先备份，再动手。** 每一步可回滚的前提是上一步留了旧版本。

> ⚠️ **前置条件**：本次改动已通过 PR 合并进 `main`，本地 `main` 已 `pull` 到最新且工作区干净。
> **任何角色都不直接推送 `main`（`gitee` 与 `origin` 两个远端都不行）**（见 [`../PROJECT_RULES.md`](../PROJECT_RULES.md) 第二节）。

### 0. 同步自检（每次上线第一步）

```powershell
git fetch --all --tags
powershell -ExecutionPolicy Bypass -File backend\check-live.ps1
```

脚本只读，核对**三处锚点**是否一致：

| 锚点 | 来源 |
|---|---|
| 线上版本 | `GET /api/health` → `data.gitSha` |
| 版本锚点 | 最近一个 `release/*` tag 指向的 commit |
| 发布总账 | `releases/发布记录.md` 是否记载该 `gitSha` |

- **一致** → 继续第 1 步
- **不一致** → 按 [`../PROJECT_RULES.md`](../PROJECT_RULES.md) 2.6.3 处理后再上线

手工等价命令（脚本不可用或想自己确认时）：

```bash
curl -s https://dsxnb.com/api/health
git tag -l 'release/*' --sort=-creatordate | head -n 1
git rev-list -n 1 <tag>
```

> ⚠️ 若线上 `gitSha` **不在任何 `release/*` tag 上**（他人分支发布 / 线上被手工改过），
> 打包必须显式指定基线，否则增量清单会算错：
>
> ```powershell
> powershell -ExecutionPolicy Bypass -File backend\build-deploy.ps1 -Name "<本次上线名>" -Base <线上 gitSha>
> ```

### 1. 备份

```bash
# 目录名用「日期-标识」，与本次上线名对应，例如 2026-09-14-admin-invite-count
BACKUP=~/eggworld/backup/$(date +%Y%m%d)-<本次标识>
mkdir -p "$BACKUP" ~/eggworld/backup/db

# ① 数据库（仅在有库变更时）
mysqldump --single-transaction --default-character-set=utf8mb4 --set-charset \
  eggworld > ~/eggworld/backup/db/eggworld_$(date +%Y%m%d_%H%M).sql
chmod 600 ~/eggworld/backup/db/*.sql

# ② 旧的后端与前端文件
cd /home/xiaos/eggworld
cp eggworld.jar "$BACKUP"/
cp xs/index.html "$BACKUP"/
cp -r xs/js "$BACKUP"/js

# ③ 验证可读（必做，不能省）
ls -l "$BACKUP" ~/eggworld/backup/db    # 属主必须是自己（xiaos），出现 root 就是错的
```

> ⚠️ **全程不要用 `sudo`**：`sudo` 建的目录属主是 root、权限 `700`，出事时 `xiaos` 读不到 —— **等于没备份**
> （2026-09-14 真实发生过：两个 backup 目录 `root:root drwx------`）。
> 备份后抽样 `test -r <文件>` / `tar tzf` 确认能打开。
>
> **只留最近 3 次**上线目录，更早的按 [PROJECT_RULES.md](../PROJECT_RULES.md) 2.3.4 的**归档判据**处理。

### 2. 数据库迁移（仅当迁移文档标注「含数据库变更」）

按迁移文档 / [docs/迁移计划.md](../docs/迁移计划.md) 指明的顺序执行 `backend/sql/migrate-*.sql`。
**线上已有库永远不要执行 `init.sql`**（开头是 `DROP TABLE`，会清库）。

### 3. 本地生成「增量部署包」（标准做法）

```powershell
powershell -ExecutionPolicy Bypass -File backend\build-deploy.ps1 -Name "YYYY-MM-DD_本次迁移文档同名"
```

脚本会自动：
- 对比 git 变更：**默认取「最近一个 `release/*` tag」为基准**（= 线上正在运行的版本），因此只会打包「上次上线之后」的改动；
  没有 tag 时（首次引导）会报错并要求显式传 `-Base <ref>`；
- **注入版本信息**：把 `version`（本次上线名）/ `gitSha`（当前 commit，工作区不干净时带 `-dirty`）/ `buildTime` 写进 jar，
  线上可用 `GET /api/health` 自查（文件打包后自动删除，不入库）；
- **后端**有变更 → 用 JDK17 重新 `clean package`，把 jar 放进包内；
- **前端**只拷本次变更/新增的文件（`growth-schoolv3.html` 自动改名为 `index.html`，`js/` 保持子目录）；
- 检出**删除的文件**，写进包内「部署说明.md」，提示在服务器删除并登记到迁移文档。

产出目录 `releases/deploy/<Name>/`，结构与服务器目标路径一一对应：

```
<Name>/
├── backend/eggworld.jar      -> /home/xiaos/eggworld/eggworld.jar
├── frontend/index.html       -> /home/xiaos/eggworld/xs/index.html
├── frontend/js/xxx.js        -> /home/xiaos/eggworld/xs/js/xxx.js
├── frontend/char-eggy-*.jpg  -> /home/xiaos/eggworld/xs/char-eggy-*.jpg
└── 部署说明.md                （上传命令 + 删除清单 + 需另行处理的变更）
```

> 「只改前端、不动后端」时，脚本不会重新打包 jar，包内只有前端文件。
> 需要**全量**重传前端（排查线上文件缺失等）时，改用 `backend\build-release.ps1`（产出 `backend/release/`，含全部 12 个外联文件）。

### 4. 上传（按「部署说明.md」照抄即可）

```bash
# 后端（包内有 jar 时）
scp releases/deploy/<Name>/backend/eggworld.jar xiaos@dsxnb.com:/home/xiaos/eggworld/eggworld.jar

# 前端（包内 frontend/ 与服务器 /xs/ 一一对应）
cd releases/deploy/<Name>/frontend
scp -r . xiaos@dsxnb.com:/home/xiaos/eggworld/xs/
```

> ⚠️ 外联文件必须与 `index.html` 内的引用同名且保持 `js/` 子目录结构；
> 新增外联文件时，务必同步更新 `backend/build-release.ps1` 的文件清单，否则全量包会少文件。
> ⚠️ **删除的文件**：按「部署说明.md」第三节在服务器 `rm`，并登记到迁移文档（见第五节规范）。

### 5. 重启服务

```bash
ssh xiaos@dsxnb.com 'systemctl restart eggworld && systemctl status eggworld --no-pager'
```

nginx 配置有变更时另需：`nginx -t && systemctl reload nginx`。

### 6. 上线验证

按迁移文档的「验证清单」逐项确认；至少包含：

```bash
# 必须能看到本次的 version 与 commit，说明新 jar 真的生效了
curl -s https://dsxnb.com/api/health
# → {"code":200,"msg":"ok","data":{"status":"up","version":"<本次上线名>","gitSha":"<commit>","buildTime":"..."}}
```

外加一次**主管理员登录 + 副管理员登录**的界面冒烟（改动涉及后台时）。
后台登录后，侧栏底部会显示「版本 · commit」，可与上面的返回值对照。

## 三、回滚

> ⚠️ **动手前先确认备份可读**（`ls -l` 属主 + `test -r`）—— 读不到就停下来找异地 / 归档副本，别在线上继续试。

| 变更类型 | 回滚方式（`$BACKUP` = 第二节第 1 步建的备份目录） |
|---|---|
| 后端 jar | `cp "$BACKUP"/eggworld.jar eggworld.jar && systemctl restart eggworld` |
| 前端入口 / 外联 | `cp "$BACKUP"/index.html xs/index.html`、`rm -rf xs/js && cp -r "$BACKUP"/js xs/js` |
| 数据库 | 用第二节第 1 步的 dump 恢复（`~/eggworld/backup/db/`）；**新增表/新增列一般向后兼容，可不回滚** |
| nginx | 恢复旧 conf 后 `nginx -t && systemctl reload nginx` |

## 四、迁移文档规范（项目约定 · 固定）

### 4.1 什么时候写

**每次上线都必须新建一份迁移文档**，无论改动大小。**时间点在 PR 阶段**：只要这次改动会随下一次上线发布，
就在提 PR 时把它写好并**随 PR 一起提交**（见 [`../PROJECT_RULES.md`](../PROJECT_RULES.md) 2.1 第 5 步）。

特别地：

- **只涉及前后端文件修改、不涉及数据库修改**时，也要单独出一份迁移文档，并在「数据库变更」一节明确写 **「无」**。
- 一次上线同时包含多轮改动（或多个 PR）时，可合并为一份，但变更清单必须逐轮列清、并链接各 PR 自带的迁移文档。
- ❌ 不要等 PR 合并后才补、也不要等上线前临时撰写 —— 那时上线执行方得把「上次 tag 之后的累计改动」重新梳理一遍，
  很容易与部署包实际内容对不上（2026-09-14 真实发生过）。

### 4.2 放哪、怎么命名

- 目录：`releases/迁移文档/`
- 文件名：`YYYY-MM-DD_<本次做了什么>.md`
  - 日期在最前，一眼看出上线时间
  - 简述用**下划线分隔的关键词**，见名知意，不要写「更新」「优化」这类无信息量的词
  - 示例：`2026-09-13_用户管理改密_副管理看板全量_注册邮箱密码校验.md`

### 4.3 必须包含的内容

1. **抬头**：日期、变更类型（`仅前后端文件` / `含数据库变更`）、关联文档、**本次部署包目录**，
   以及**上线前 / 上线后线上 `gitSha`**（各来自一次 `curl -s https://dsxnb.com/api/health` 实测）。
   上线后那个值在上线时回填（见 4.5 第 10 步）—— 文档据此**自证已上线**，不必日后靠 jar mtime 反推
2. **本次范围**：一句话说清做了什么、为什么
3. **变更清单**：文件级明细，**每行写清「仓库文件 → 服务器绝对路径」**（路径写错是上线最常见的低级事故），
   并标注每个文件「参与部署 / 仅测试」
4. **文件删除**：逐条列出本次删除/重命名的文件及其服务器路径；**无则写「本次无删除」**
   （`build-deploy.ps1` 会自动检出并写进部署包的「部署说明.md」，两边必须一致）
   - 删除前按 [PROJECT_RULES.md](../PROJECT_RULES.md) **2.3.4 的归档判据**判断：别处有副本的（前端文件、jar）**直接删**；
     只存在于服务器的（库 dump、他人项目文件）**先归档再删**（`archive/<名>-<日期>.tar.gz` + 刷新 `SHA256SUMS`），
     归档名登记在本节 —— **服务器 `archive/` 只是中转站**，异地备份核对后只留最近 1 个批次
5. **数据库变更**：有则写全 —— 脚本（`backend/sql/migrate-*.sql` → `/home/xiaos/eggworld/sql/migrate-*.sql`，线上已有同文件时先比对内容）、
   内容（只 `CREATE` / 有无 `ALTER DROP TRUNCATE`）、**库备份命令**（`mysqldump -u eggworld -p eggworld > ~/eggworld/backup/db/eggworld_$(date +%Y%m%d_%H%M%S).sql`，
   `chmod 600` 后抽样验证可读）、执行顺序（**先在服务器建表，再切 jar**）与确认命令；**无则必须写「无」**。
   账号是 `eggworld`，密码不写进文档；**永远不执行 `init.sql`**（线上那份已另存为 `~/eggworld/backup/init.sql.READONLY-禁止执行`）
6. **部署步骤**：本次实际要执行的命令 —— **必须含「本地生成增量部署包」这一步**
   （`powershell -ExecutionPolicy Bypass -File backend\build-deploy.ps1 -Name "<同名>"`，见第二节第 3 步），
   再写服务器侧动作（备份 → 库迁移 → 上传 → 重启 → 版本自查 → 删除项默认不执行）；可只列与标准流程不同的部分
7. **验证清单**：可勾选的、具体到页面的验收项
8. **回滚方案**：保留哪些旧文件即可还原
9. **备注 / 已知边界**：遗留问题、权限边界、后续计划

### 4.5 标准动作（每次更新固定如此）

> ⚠️ **顺序不能颠倒**：先 commit（并经 PR 合并进 `main`）再打包，jar 里的 `gitSha` 才等于 tag 指向的提交；
> 若先打包后提交，jar 会带 `-dirty`，版本锚点就失去自证能力。

1. 改代码 → 本地自测（测试命令清单见 [`../PROJECT_RULES.md`](../PROJECT_RULES.md) 2.2）
2. 写迁移文档（本节规范，文件名 = 本次上线名）—— **随下面第 3、4 步的同一个提交与 PR 一起提交**，不要等上线前才补
3. 在分支上 `git commit`（把本次改动 + 迁移文档一起提交）
4. `git push -u gitee <分支>` → 开 PR → **双方确认后合并 `main`**（`main` 禁止直推）
5. 切回 `main` 并 `git pull`，确认工作区干净、`HEAD` 就是要发布的那个提交
6. 跑 `backend/build-deploy.ps1 -Name "<同名>"` 生成增量部署包（自动以上个 tag 为基准）
7. 按包内「部署说明.md」上传 / 删除 / 重启
8. 按迁移文档的验证清单逐项确认，其中**必须确认 `/api/health` 返回本次 version**
9. `git tag -a release/<日期> -m "<本次上线名>"` + `git push gitee --tags`
10. 回填 [发布记录.md](发布记录.md)（版本 / commit / 结果）与迁移文档抬头：
    「**上线后**线上版本」填本次实测 `gitSha`（「上线前」那个值写文档时已填），使文档自证已上线
11. 如与「部署说明.md」的删除项有出入，回头补齐迁移文档（删除按 **2.3.4 归档判据**执行并留证）

### 4.6 版本锚点（git tag）

**tag 就是「线上正在跑的那一版」的锚点**，没有它就无法回答「线上是哪一版」「上次之后改了什么」「回滚到哪」。

- **命名**：`release/YYYY-MM-DD`；同一天发多次时加**关键词后缀**（见名知意优先）或序号，如
  `release/2026-09-14-checkin-pk`、`release/2026-09-13.2`
- **指向**：上线验证**通过之后**，打在该次上线对应的提交上（不是提前打）
- **推送**：`git push gitee --tags`，让远端也有锚点（`main` 此时已由 PR 合并推送过，无需再推；`origin` 是 GitHub 备份，需要时再单独推）
- ⚠️ **tag 指向的提交必须已在远端**：打 tag 前先确认该提交已推送。
  线上跑着一个远端不存在的提交，等于版本无法自证 —— **无法 review、无法回滚、也算不出增量基线**
  （2026-09-14 真实发生过，`check-live.ps1` 报「线上 gitSha 在本仓库中不存在」）
- **自证**：jar 内置 `version/gitSha`，`curl /api/health` 可核对 tag 与线上是否一致
- **增量基准**：`build-deploy.ps1` 默认以上个 `release/*` tag 为基准算「本次要传什么」

```bash
# 上线验证通过后
git tag -a release/2026-09-13 -m "用户管理改密 + 副管理看板全量 + 注册邮箱密码校验"
git push gitee --tags

# 随时核对：线上跑的是哪个 tag
curl -s https://dsxnb.com/api/health
git log -n 1 --oneline release/2026-09-13
```
