# 「用户猫上公园」改造评估（2026-10-10）

## 背景与目标

现状分两层：
- **线上（04159ae）**：公园「他人猫」= `MOCK_USERS` 假数据 + `Math.random()` 模拟繁育，用户之间互不可见。
- **分支（feat/cat-park-breeding，未上线）**：繁育交互已是服务端权威（真实账号归属、通知、同意/拒绝、48h 冷却、好感度、幂等领取），但目录猫是迁移 SQL 预置的 5 只固定猫，**不是用户存档里养的那只**。

目标：让用户把自己存档里的猫「放到公园」后，其他真实用户能看到这只猫并发起繁育申请；归属者同意/拒绝；后代回给双方（待定）。

### 好感度模型（2026-10-10 与负责人确认，修正原设计）

原需求「发起用户与目标猫好感度≥Lv.2」在用户猫模型下**语义变更**为：

> **繁育资格 = 双方各自与自己那只猫的好感度 ≥ Lv.2**
> - 发起方：他用来繁育的那只猫（applicant），与**他自己**的好感度 ≥ Lv.2
> - 归属方：他的目标猫，与**他自己**的好感度 ≥ Lv.2（作为猫主人才有资格让爱猫繁育）

关键收益：这两个好感度**本来就存在于双方存档里**（`cat.intimacy` / `cat.level`，喂食/玩耍/专注累积），因此：
- 用户猫上公园后，**不需要**「陌生人对别人猫刷互动攒好感度」这套东西；
- 当前分支的 `cat_affinity` 表 + `POST /cats/{id}/interact` 端点（为固定目录猫设计，目录猫没有真实主人存档才需要外挂好感度）在用户猫模型下**属于过渡产物，应废弃**，避免两套好感度体系并存；
- 服务端只需在 reconcile 时把猫的 `affinity_level`（连同 `maturity_level`）快照进 `park_cats`，申请时直接读快照校验，无需新表、无需互动接口。

固定目录猫（official 5 只）的门槛处理见文末「待产品决策」第 5 条。

## 核心矛盾与选型

**矛盾**：猫名册是客户端存档权威（整份 JSON 防抖回写），公园/繁育是服务端权威。服务端如何得知「谁的哪只猫在公园、现在什么状态」？

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 显式发布 API | 放公园/带回家时前端调 `/park/publish`、`/unpublish` | 改名、换设备、送猫/捐赠后忘调 API → 快照漂移、幽灵猫，需一堆补偿接口 |
| B. 存档回写时同步提取 | 服务端在 `saveState` 落库时解析 cats，按 `cat.inPark` 标志 upsert 公园名录 | **推荐**。名册唯一源仍在存档；公园名录是确定性投影，改名/属性漂移/删猫自愈 |
| C. 服务端接管名册 | 猫状态全部入库 | 推翻现有 P1/P2 架构，改动面爆炸，否决 |

**方案 B 关键前提**：`inPark` 必须挂在**猫实例（uid）上**而不是现在的 `state.catsInPark` 下标数组（uid 是 `createCat` 生成的稳定标识，下标在送猫/捐赠/替换后会错位——引擎自己就在做 index 重映射，见 sendCat/donateCatToHome）。

**防伪造边界**：save JSON 客户端可控，但名录只影响「别人看到什么」；繁育资格（双方好感度/成年）取自各自存档快照，刷高自己猫的 level 等价于刷自己存档等级（现有喂食/专注体系本就如此，风险与存档其它玩法一致）；与假猫繁育仍需 owner 同意 + 冷却，无利可图。服务端仍校验字段合法性（breedId 在品种表内、名字长度、性别枚举、level 单调不倒挂）。

## 改造清单

### 后端（中等改动，演进现有模块而非重写）

1. **`park_cats` 表扩展**（迁移 `migrate-cat-park-user-cats.sql`）：
   - 加列：`source`（official/user，official 保留现有 5 只固定 id 1..5）、`cat_uid`（存档 uid，`UNIQUE(owner_user_id, cat_uid)`）、`rarity_level`、**`affinity_level`**、**`maturity_level`**（reconcile 从存档快照，繁育资格校验依据）、`gender` 已有、`parent_uids`（JSON，近亲检查用）、`listed_at`
   - 用户猫 id 从 6+ 自增；`breeding_requests` 的 `park_cat_id` 外键**零改动**（同一 id 空间）
   - `cat_affinity` 表：标记为过渡产物，用户猫上线后**下线**（迁移文档中登记 DROP）
2. **`CatCabinService.saveState` 挂钩 `CatParkService.reconcileFromSave(userId, save)`**：
   - 遍历 `save.cats`：`inPark=true` 且合法 → upsert 名录行（同步名字/性别/稀有度/**affinity_level/maturity_level**/parent_uids 快照）；
   - 已有行但猫不再 `inPark`/已从存档消失 → 置下架（`deleted=1`）；
   - 繁育冷却中的猫下架：保留 `last_breed_time`（重新上架不重置冷却，防绕过）
3. **`listCats` 合并展示**：official + 他人 listed 用户猫（含主人昵称、冷却、猫的繁育资格状态）；**去掉「我的好感度」列**（用户猫模型下不适用）；上限沿用 `maxCatsInPark=3`/人
4. **繁育校验补强**（按新好感度模型，闭合现有漏洞）：
   - 归属方门槛：读 `park_cats.affinity_level`（主人快照）≥ Lv.2，否则该猫显示「主人好感度不足，暂不可繁育」
   - 发起方门槛：`applicantCatUid` **服务端校验**——查发起方自己的名录/存档快照，确认该 uid 属于本人、`maturity_level>=3` 且 **`affinity_level>=2`**（现在只信前端，且只查成年不查好感度）
   - 后代裁决升级为双亲决定：`offspring = f(applicant.breed, target.breed)`，近亲检查（parent_uids 三代求交，祖先未上过公园则查不到 → 尽力而为，见风险）
   - 移除 `POST /cats/{id}/interact` 与 `cat_affinity` 相关分支逻辑（official 猫的处理见待决策第 5 条）
5. **通知/领取**：`accept` 时双方各生成一条可领取后代（若产品定「一人一只」）；`claim` 幂等机制不变

### 前端（小-中改动）

1. `putCatInPark/takeCatHome` 改写 `cat.inPark` 标志（保留旧数组兼容或直接迁移，初始化时按标志重建）
2. 社交区三 tab 已就绪，用户猫自然流入 `GET /cats`；**去掉「🫳 互动 +好感」按钮**（新模型下陌生人不刷好感），申请弹窗里对「好感度<Lv.2 的繁育猫」给出前置引导（引导内容改为「先把你和这只猫的感情养到 Lv.2——喂食/玩耍/专注陪伴」）
3. **旧 mock 公园必须让位**：canvas 场景里「他人猫」改为渲染服务端真实用户猫（或隐藏他人区，只留流浪猫抽卡玩法）——两套并存会让用户再次误以为假猫是真人的（本次误解的根源）
4. 领取后代弹窗展示双亲信息；改名入口无需改动（reconcile 自动同步）

### 测试

- 单测：reconcile 幂等/下架/冷却保留/伪造字段拒绝/**affinity_level 快照随回写更新**；双亲后代裁决确定性；applicantCatUid 越权/未成年/**好感度不足**拦截；目标猫主人好感度不足拦截
- e2e 扩展：A 放真猫上公园 → B 的 `/cats` 可见 → B 申请（A 猫 Lv.1 → 拦；A 猫升到 Lv.2 → 放行）→ A 同意 → 双方领取 → A 改名后 B 端快照更新 → A 送猫/捐赠后 B 端自动下架 → 冷却中重新上架不重置

## 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 存档回写延迟 | 放公园后最长 5s（防抖）别人可见 | 可接受；publish 动作即时 flush 一次即可消除 |
| 近亲检查不完整 | 祖先从未上过公园则无谱系数据 | 尽力而为 + 文档注明；后续可给全部猫入库族谱 |
| saveState 解析成本 | 每次回写解析 ≤256KB JSON | 低频（防抖+行锁已在），实测几十 KB，可接受 |
| 双端下标语义迁移 | 老档 `catsInPark` 是下标 | 首次加载按 uid 写 `inPark` 标志，一次性迁移 |
| 下架猫的申请残留 | pending 申请指向已下架猫 | 同意时复查 `deleted` → 自动拒绝 + 通知（复用 blockedResult 模式） |

## 工作量与分期

- **P1（核心闭环）**：表扩展 + reconcile + listCats 合并 + applicantCatUid 校验 + 前端 inPark 标志 + mock 他人猫下线 —— 一个分支内可完成、可独立上线
- **P2（体验完善）**：双亲后代裁决 + 近亲检查 + 双方各领一只 + 公园 canvas 真实猫渲染
- 上线均需迁移文档（含数据库变更：ALTER + 新列，先建表后切 jar），owner 绑定说明不再需要（用户猫天然有主）

## 待产品决策

1. 后代归属：仅发起方领（现状）还是**双方各一只**（生物学直觉，mock 版就是 2 只）？
2. 是否要求**异性**才能繁育（现模型不校验性别）？
3. 旧「换一批抽卡公园」去留：他人区换真实猫后，流浪猫抽卡保留？
4. 公园展示位上限沿用每人 3 只？
5. **固定目录猫（official 5 只）的去留**：新好感度模型下它们没有真实主人存档，`cat_affinity`+`/interact` 这套外挂好感度要么保留（两套体系并存）、要么给它们预置「主人好感度达标」直接走新校验、要么**用户猫上线时一并下线 official 猫**（推荐——公园从此只有真猫）。
