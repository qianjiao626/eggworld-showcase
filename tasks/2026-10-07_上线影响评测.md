## 五、数据库影响

- **顺序**：备份（`mysqldump` → `~/eggworld/backup/db/`、`chmod 600`、抽样可读）→ **3 个建表/加列**（announcements、gossip-reports、task-proof-image）→ 1 个归档（chatroom-channels）→ 确认 → 最后切 jar。**职业测评 / 宠物系统 / 猫舍的 3 个脚本本轮不执行**。
- **锁与时长**：`tasks` 只加可空列 + 索引（MySQL 8 属 instant/轻量；**若线上是 5.7/MariaDB 则 `ADD COLUMN` 会重建表**，建议先 `SELECT VERSION()`）；`cat_reward_grants` 的条件 `ALTER` 会重建唯一键；`chat_conversations` 的归档是一条带条件的 `UPDATE`（非破坏性、不 `DELETE`）。
- **可回滚性**：新增表/列**向后兼容、可不回滚**；唯一可逆项是频道归档（`UPDATE ... SET status='active'`）；`tasks.proof_image_id` 可长期保留（旧 jar 不读它）。
- **不要做的事**：不执行 `init.sql`（含 19 条 `DROP TABLE`）、不执行 `migrate-chatroom.sql`（种子）、不删用户图片、不为回滚反向冲正资金。
- **顺序错误的爆炸半径**（最容易犯的错）：jar 先切、表未建时，公告（首页每次加载）、爆料、证明图接口报 `code:500`，**任务模块整体不可用**（`proof_image_id` 缺列）；此时唯一正确动作是立刻建表，而不是回滚 jar。**职业测评 / 宠物系统 / 猫舍不受影响** —— 它们本轮就不建表，缺表时由模块闸返回 `code:404 该功能暂未开放`。

## 七、安全与隐私

- **正面**：本批带来 WebSocket 鉴权、分层限流（真实 429 + `Retry-After`）、验证码原子防刷、注销清理补齐、路径参数类型校验（不再回显内部异常）、公告也走敏感词校验。
- **需接受或修复**：证明图公开可枚举（第一节 🟠，含未过审任务的图）——这是本次唯一「新增的隐私暴露面」。
- **匿名读白名单被放宽**：`JwtInterceptor` 把公告/爆料的公开读正则从 `\d+` 改成 `[^/]+`（`JwtInterceptor.java:53-66`）。已逐个核对（本次做了全量映射审计）：
  - 实际被匿名放行的读路径只有公告、爆料、吐槽、任务广场/详情、`by-nickname`、宿舍、证明图这几类，**没有因此泄露应登录数据**（爆料/公告都强制 `status='published'`，未登录读 `UserContext` 的调用方全部容忍 null，**无 NPE**）。
  - **唯一错位**：`GET /api/complaints/mine` 自己的 javadoc 写着「需登录」，却因 `startsWith("/api/complaints/")` 被放行（排除项只写了 `my-posts/my-published/my-claimed`）；所幸 service 主动抛 401，**不泄露数据**。建议后续补 `mine` 到排除项（P1）。
  - **结构性风险**：这两个前缀下**将来新增的任何 GET 都会被自动匿名放行**（这是 `[^/]+` 写法的副作用），值得在下次改鉴权时收紧为具体路径枚举（P2）。
- **写接口没有被误放行**：白名单第一层就要求 `HttpMethod.GET`，POST/PUT/DELETE 一律走登录校验（`JwtInterceptor.java:64,92-98`）；只有 OPTIONS 预检与 `POST /api/track/page`（游客埋点）是有意放行。
- **错误信息回显**：兜底分支把 `e.getMessage()` 回显给前端（含表名/SQL 片段），匿名接口也一样 —— 轻微信息泄露，且让「按状态码监控」失效（见第一节与第十一节）。
- **上传侧**：必须登录（匿名 `POST /api/tasks/proof-images` → 401）、只信真实文件头（复用 `DormitoryImageValidator`）、≤5MB、响应带 `X-Content-Type-Options: nosniff`。
- **注意**：`GlobalExceptionHandler` 的兜底分支会把内部异常文本回显给前端（历史行为），上传受限时用户看到的可能是模糊错误，排查要靠服务器日志。

✅ **已修（2026-10-07）**：以下「IP 额度 = 全站额度」描述的是**修复前**的状态。现在 `ApiTrafficInterceptor.clientIp()` 只在直连对端是回环（本机 nginx）时读 `X-Real-IP`（nginx 用 `$remote_addr` 覆写该头），其它来源一律用 TCP 对端地址，`X-Forwarded-For` 依旧不读 → **不需要动 nginx、也不需要 `real_ip`**；回归见 `ApiTrafficClientIpTest`（回环分桶 / IPv6 回环 / 非回环伪造无效 / 缺头回落）。以下内容保留作为背景与被否决方案的记录：

- 拦截器只取 `getRemoteAddr()`（`ApiTrafficInterceptor.java:37-38`），而线上 nginx 把 `/api/`、`/ws/` 反代到 `127.0.0.1:8090`（`backend/deploy/dsxnb.conf:101-126`）；仓库 conf 只设了 `X-Real-IP` / `X-Forwarded-For` 头（`:105-108,123-126`），**没有 `real_ip` 配置**，Spring 侧也没有 `server.forward-headers-strategy`。
- 后果：所有真实用户被算作同一个 IP（`127.0.0.1`），于是上表「IP 列」变成全站每分钟上限 —— **认证 120、验证码 120、上传 200、写 1200、读 6000**。上课高峰/迎新批量登录时，**全站登录、注册、发验证码会集体 429**；上传档更容易被证明图 + 宿舍图一起打满。
- 这不是本批 PR 引入的代码缺陷，但**会随本批首次在线上生效**；而且 `!25` 自带文档已把它登记为**发布阻断项**（`releases/迁移文档/2026-10-02_高并发与安全加固.md:161,174`、`docs/backend-handoff.md:1284`），至今未修。
- 修法（服务器侧，需授权）：
  1. **推荐**：nginx 侧启用 `real_ip`（`set_real_ip_from 127.0.0.1; real_ip_header X-Forwarded-For; real_ip_recursive on;`），让 `getRemoteAddr()` 拿到真实客户端 IP（`proxy_add_x_forwarded_for` 追加的最右一跳即真实地址，客户端伪造左侧无效）；
  2. 或让应用信任 `X-Real-IP`（需同时确认 nginx 用 `$remote_addr` 覆写该头，否则可被伪造）；
  3. **临时兜底**：在线上 `application-prod.yml` 把 `eggworld.traffic.*` 的 IP 档调高到「当全站额度也够用」的量级（代价是削弱抗刷能力）。
- 验证方式：上线前/后从两个不同出口 IP 各打几次请求，确认计数是分开的（`nginx -T` 确认真实配置 + 用一个超限脚本对比两侧是否独立计数）。
- 另外：**所有限流计数只在单实例内存里**（`maxKeys 20000`），一旦扩到多实例，实际总量 = 配置 × 实例数。

- 超限返回**真实 HTTP 429 + `Retry-After`**（`RateLimitException.java`、`GlobalExceptionHandler` 的 `handleRateLimit`），前端必须按状态码处理。
- **分页守卫**：`page 1–10000`、`size/limit 1–100`，越界直接 400（`ApiTrafficInterceptor.java:49`）。已核对现有前端最大用 `size=100`，不会被误伤；但**旧的缓存 JS** 若发过大 size 会拿到 400（本批已给变更文件升 `?v=`）。
- **WebSocket**：单实例 2000 连接、**单用户 5 连接**、单连接 128 订阅、订阅尝试 256/分、消息 ≤16KB（`AppProperties.java:84-91`）。用户开 6 个标签页/多设备会被拒 —— 上线后值得观察聊天室报错率。
- **聊天发送**：进程内滑动窗口 3 条/秒（多实例部署必须换 Redis）。
- **内存**：证明图上传/读取都是整图进堆（≤5MB/请求，`TaskProofImageService.java:57`、`:133`）；上传档位限制到 20/分/账号，风险可控但值得盯 GC。
- **单实例前提**：所有限流计数在**单实例内存**中，多实例部署会让「实际总量 = 配置 × 实例数」。
