## 一、目标与结论边界

**目标：先堵住资源滥用和权限缺口，再减少聊天、任务列表的负载放大，最后以隔离压测确定实际容量。**

- 不预先承诺“支持 1000 人 / 1 万人在线”；连接数、活跃人数、请求速率、消息速率分别计量。
- 不把应用限流当作 DDoS 防护能力的证明；云防护、带宽、源站入口另行核实。
- 用户提到的“ROIS”具体含义待澄清，本工单先覆盖 DDoS、CC 刷接口、验证码滥用和实时通道越权。
- 本工单获准执行不等于获得生产变更授权。生产压测、部署、Nginx/WAF 调整、数据库迁移和付费服务采购均需单独确认。

### SEC-01｜实时通道鉴权与资源边界

**当前进展：**连接/订阅/出站默认拒绝、账号与成员复核、客户端 SEND 禁止、连接/订阅/缓冲/首帧上限已实现。订阅和出站授权由三次独立查询合并为一次即时 JOIN，不缓存权限；CONNECT 仍独立检查账号及逻辑删除状态。每会话每分钟 256 次订阅尝试在 SQL 前扣预算，取消订阅不返还额度；重连重置预算，不等于账号级建连防洪泛。权限服务 6 项（新增 2 项）、授权单测 14 项及 SockJS WebSocket/XHR 两项真实传输共 22 项通过。出站授权点是 preSend，不保证撤回已通过检查的排队帧；广播仍逐收件人执行一次查询，慢消费者及生产容量未测。

**问题证据：**
- `backend/src/main/java/com/eggworld/config/WebSocketConfig.java` 的入站拦截器只在 `CONNECT` 时校验登录，未见针对 `SUBSCRIBE` 的会话成员校验或客户端广播目的地限制。
- `backend/src/main/java/com/eggworld/service/ChatRealtimePublisher.java` 将会话事件发布到广播主题。
- REST 会话权限不能替代 STOMP 订阅授权。存在已登录用户越权订阅或伪造事件的代码风险，未在生产尝试利用。

**实施要求：**
1. 采用默认拒绝策略，对连接、订阅、发送分别鉴权；订阅校验活跃会话、有效成员和账号状态。
2. 禁止客户端向服务端广播主题直接发布；保留已授权的业务发送入口，不破坏现有 REST 发送流程。
3. 处理封禁、退群、踢出等权限撤销：已建立的订阅也必须失效，不能只在首次订阅时判断。
4. 明确连接数、订阅数、消息体、发送缓冲和慢消费者策略；参数配置化，兼容必要的 STOMP 控制帧与 SockJS 传输。

**验收：**
- [x] 本地测试覆盖未登录、过期 Token、非成员、已退出/封禁用户与合法成员；只用隔离测试账号。
- [x] 非成员不能订阅他人会话；撤销后新进入 preSend 的受保护事件不再投递（真实双传输已测；已排队帧的即时撤回不在本轮保证中）。
- [x] 客户端不能绕过业务校验向广播主题注入事件。
- [ ] 合法发送、订阅、心跳、断线重连和历史消息读取无回归。
- [ ] 超限或慢连接被可控处理，不拖垮其他用户；日志不记录 Token 和消息正文。

### SEC-02｜分页上限与接口分层限流

**当前进展：**page 1..10000、size/limit 1..100、MyBatis maxLimit 100；JWT 前 IP/global、JWT 后账号预算及匿名登录/注册邮箱预算已实现，返回真实 429 + Retry-After。单实例固定窗口、有界缓存；不读客户端转发头。未改/验证 Nginx、可信代理或真实校园出口；multipart 限流晚于解析，不能代替边缘保护。

**问题证据：**
- `backend/src/main/java/com/eggworld/dto/TaskQueryDTO.java` 的分页参数没有上限约束。
- `TaskService.java` 的 `listTasks` 直接把请求页大小传入分页查询，`MybatisPlusConfig.java` 未设置全局最大页大小。
- `backend/deploy/dsxnb.conf` 仅对 `/api/auth/` 明确配置请求限流，普通 API 未见同等规则；线上是否生效尚未核实。

**实施要求：**
1. 盘点全部用户可控分页/查询参数。建议默认 20 条、上限 100 条；逐接口核对现有调用后确定，不机械修改所有默认值。
2. 非法、负数或超限输入在进入重查询前拒绝；错误遵循项目响应规范，不能静默变成全量查询。
3. 对登录、验证码、搜索/列表、上传和写操作分别制定配额；结合账号与 IP，不能只有一个全站阈值。
4. 明确限流窗口、突发额度、恢复时间和存储故障策略；被限流返回 HTTP 429，并给出可理解的重试提示。
5. 校园共享出口纳入误伤测试；客户端自报转发头不能直接成为可信身份，代理真实 IP 规则需运维确认。

**验收：**
- [x] 边界测试覆盖省略参数、零、负数、上限、超限和溢出；正常翻页与现有 size=50 调用保持兼容。
- [x] 应用单测验证账号/IP/global 预算、窗口恢复、匿名登录/注册邮箱预算在昂贵业务前生效；上传解析前的边缘保护另列待验收。
- [x] 应用测试中伪造转发头不能绕过以 RemoteAddr 为来源的限制。
- [ ] 在实际可信代理链/共享校园出口验证合法用户不被整体限流。
- [ ] 本地 Nginx 配置测试与应用回归通过；报告明确区分仓库配置和生产有效配置。

### SEC-03｜验证码原子防刷与缓存治理

**当前进展：**锁内原子预留、锁外发信；发送中互斥、失败/超时保留冷却、一次消费、5 次错码、TTL/容量/全局预算已实现。专项 16 项通过（并发 7、邮件 6、聚合指标 3）；另补红→绿回归移除旧开发降级日志中的邮箱/验证码；脱敏聚合配额日志在有变化时最多每 60 秒输出一次，空闲静默，不公开诊断接口。生产 SES 配置仍需核实，缺配置降级不代表可用的线上发信。

**问题证据：**`VerifyCodeService.java` 采用“检查冷却 → 发邮件 → 写缓存”的流程，存在并发检查窗口；验证码保存在进程内 Map，未见容量上限与定期过期清理。

**实施要求：**
1. 原子占用发送名额，同邮箱在同一冷却窗口内只允许一个有效发送任务进入邮件调用。
2. 定义发信失败、超时和不确定结果的处理；失败清理不能误删后来的有效状态，也不能形成无限快速重试。
3. 保留现有 5 次错误限制、一次性消费及发送冷却；增加容量上限、过期清理和配额指标。
4. 增加邮箱、IP 和全局发送预算；如未来扩多实例，再单独评估共享状态，不默认引入 Redis。

**验收：**
- [x] 同邮箱多线程竞争仅产生一次获准发送；不同邮箱不会被全局串行锁无谓阻塞。
- [x] 验证码并发验证只能成功消费一次；第五次失败不会重置发送冷却。
- [x] 超时/失败后的重试与额度行为符合定义，过期数据可回收，缓存不会无界增长。
- [x] 自动测试使用邮件桩或沙箱，不能发送真实验证码、消耗生产邮件额度或落日志泄露验证码。

### PERF-01｜聊天请求放大与未读数优化

**当前进展：**100 条已知会话消息零次全列表刷新；未知会话合并、1000 个事件 ID 去重、新旧响应及账号/连接代际隔离、登出清理、STOMP ERROR 停止重连已覆盖。未读改单条参数化批量 UPDATE；本地微基准已对比 50/100/500 名接收成员，但未采集锁等待和完整广播成本。

**问题证据：**
- `js/chatroom.js` 每收到消息都会调用 `loadConversations()`，引发全量会话刷新。
- `ChatMessageService.java` 每条消息逐一更新所有有效成员的未读数，包括不在线成员。
- 会话列表组装还存在逐会话查库。

**实施要求：**
1. 消息事件就地更新对应会话、预览和排序；必要的校准刷新合并执行，避免每消息一次全列表请求。
2. 未知会话、重连补偿、未读同步和切换会话保留校准入口；防止旧响应覆盖新状态。
3. 第一阶段减少逐成员 SQL 往返，评估批量更新并记录锁等待；批量 SQL 仍可能更新多行，不能宣称已经消除成员数带来的成本。
4. 如果批量方案仍不达标，再评审“消息序号 + 已读位置”等模型变更。新增字段、索引和数据迁移须另行批准。

**验收：**
- [x] 确定性客户端测试中，已知会话连续收到 100 条消息，不再产生 100 次全列表拉取；无校准事件时应为零次全列表拉取。
- [x] 确定性测试验证新建 SockJS transport、未知会话/显式刷新合并、在途响应与账号切换隔离；实际弱网恢复另测。
- [ ] 发送、撤回、已读、@提醒、会话排序、群聊归档及权限撤销无回归。
- [ ] 固定成员规模下记录优化前后每消息 SQL 次数、行更新数、事务时长和锁等待；不能只报告“代码已批量化”。
