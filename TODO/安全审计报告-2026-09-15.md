## 一、执行摘要

### 1.1 总体结论

项目的**基础安全架构是扎实的**：JWT 鉴权链路完整且防御正确（`verifyWith(SecretKey)` 已阻断算法混淆攻击）、BCrypt 加密存储口令、`@AdminOnly/@ModeratorOnly` 切面覆盖全部 28 个管理端接口、**横向越权（IDOR）防御几近完备**——所有带资源 ID 的写接口均做了归属校验、原生 SQL 全部使用 `#{}` 参数占位（未发现 SQL 注入）。

**但存在三类体系性缺陷**，且均可直接转化为**资金损失或账号接管**：

| 类别 | 核心问题 | 影响 |
|------|---------|------|
| **A. 经济系统可被凭空铸币** | 组队任务驳回时按 `reward` 退款而非实际冻结的 10 币；悬赏采纳/惰性退款无并发幂等 | 攻击者可无限刷取蛋蛋币，破坏整个经济体系 |
| **B. 存储型 XSS → 令牌窃取** | 前端存在「先转义渲染 → 读回原文 → 再次注入」的双解码绕过，以及多处昵称/校名漏转义 | 任意用户可对全体用户（含管理员）执行任意 JS，窃取 JWT → 接管账号 |
| **C. 凭证硬编码于代码库** | 主管理员明文口令、JWT 默认密钥、DB 默认口令均写在源码/配置中 | 任何接触源码者可伪造管理员令牌或直接登录后台 |

其中 **B 与 C 组合可形成完整攻击链**：存储型 XSS 窃取 token → 若生产 JWT 密钥未更换，攻击者还可离线伪造任意用户（含管理员）令牌。

### 2.2 评分口径说明（重要）

- **危害度**：基于「影响面 × 可利用性 × 影响持续时间」的专家判定，**非**正式 CVSS 计算值。报告中不使用伪精确的 CVSS 分数。
- **ROSI（Return on Security Investment）**：衡量「每单位修复投入所换取的风险降低幅度」，采用五级定性评级：
  - ★★★★★ 极高 = 低成本 + 严重/高危害（应优先处理）
  - ★★★★☆ 高 = 低成本 + 中危害，或中成本 + 高危害
  - ★★★☆☆ 中 = 成本与收益相当
  - ★★☆☆☆ 低 = 高成本 + 中低危害
- **修复成本**：低 ≈ 单文件数行改动；中 ≈ 单模块改造；高 ≈ 跨模块架构调整。

### 【H-01】🔴 严重 — 组队任务审核驳回按 `reward` 退款，凭空铸币

- **文件**：`backend/src/main/java/com/eggworld/service/TaskService.java:238-240`
- **ROSI**：★★★★★（修复成本 0.5h）

**证据**：

```java
// 发布 team 任务：固定只冻结 TEAM_DEPOSIT = 10（TaskService.java:102-105）
} else if ("team".equals(dto.getTaskType())) {
    pointService.changeBalance(userId, -TEAM_DEPOSIT, "freeze",
            "发布组队任务出资：" + dto.getTitle(), task.getId());
}
```

```java
// 驳回：无条件按 task.getReward() 退款（TaskService.java:238-240）
pointService.changeBalance(task.getPublisherId(), task.getReward(), "refund",
        "任务审核驳回退回：" + task.getTitle(), taskId);
```

**校验前置条件**（已核实）：`PublishTaskDTO.reward` 仅有 `@Min(1)`，**无 `@Max` 上限**。

**攻击步骤**：
1. 发布 `taskType=team` 任务，`reward` 填 `999999`（前端不限制、后端不校验上限）；
2. 系统仅冻结 **10** 币（余额 ≥10 即可）；
3. 管理员/副管理员在审核中心点击「驳回」；
4. `reject` 按 `reward` 退款 → 账户凭空增加 `999999 − 10` 币；
5. 重复发布 + 驳回，可无限增发。

**影响**：破坏整个蛋蛋币经济体系与排行榜公信力。由于驳回是审核中心的常规操作，隐蔽性高。

**修复建议**：
```java
// 退款金额必须与实际冻结口径严格一致
int refund = "team".equals(task.getTaskType())
        ? TaskService.TEAM_DEPOSIT   // 组队固定 10
        : task.getReward();          // 求助型按悬赏额
pointService.changeBalance(task.getPublisherId(), refund, "refund",
        "任务审核驳回退回：" + task.getTitle(), taskId);
```
**根治建议**：在 `tasks` 表新增 `frozen_amount` 字段，发布时落库实际冻结额，**所有退款一律读该字段**，杜绝"按状态分支重算"的散落逻辑。同时为 `reward` 增加 `@Max(10000)`。

**攻击步骤**（全部在任务创建后 48 小时窗口内完成）：
1. 发布 `teach` 教学任务；
2. 审核通过 → 受害者认领 → 发布者配对（任务进入 `in_progress`）；
3. 受害者完成并提交 → **认领者被扣 `reward`，发布者入账 `reward`**；

### 【H-04】🟠 高 — 悬赏采纳无行锁，并发重复发放奖励

- **文件**：`backend/src/main/java/com/eggworld/service/GossipService.java:300-337`
- **ROSI**：★★★★☆

**证据**：

```java
GossipPost post = postMapper.selectById(postId);       // 普通读，无 FOR UPDATE
```

**攻击步骤**：对 `POST /api/gossip/posts/{id}/adopt` 并发 N 次（或并发两个不同 `answerId`）。所有请求都读到 `adopted=0` 并通过校验，各自执行 `changeBalance(+bounty)`。行锁只保护回答者余额增量，**不保护"是否已采纳"的判定** → 悬赏被重复发放 N 次，平台凭空多出 `(N−1)×bounty`。

**修复建议**：改为条件更新抢占：
```java
// Mapper 新增条件更新，affectedRows==1 才发奖
int rows = postMapper.markAdopted(postId);   // UPDATE gossip_posts SET adopted=1, coin_status='awarded'
                                             // WHERE id=? AND adopted=0
if (rows != 1) throw new BusinessException("已经采纳过啦");
```

### 【H-05】🟠 高 — 惰性退款无锁，读接口可被并发触发重复退款

- **文件**：`backend/src/main/java/com/eggworld/service/GossipService.java:344-356`
- **调用点**：`listPosts:55`、`detail:97`、`myPosts:112`（**只读接口的副作用**）
- **ROSI**：★★★★☆

**证据**：

```java
private void refundExpired() {
    List<GossipPost> expired = postMapper.selectList(... eq(coinStatus, "frozen")
            .lt(GossipPost::getDeadline, LocalDateTime.now()));
    for (GossipPost p : expired) {
        p.setCoinStatus("refunded");
        postMapper.updateById(p);                    // 无锁、无条件更新
        pointService.changeBalance(p.getPublisherId(), p.getBounty(), "gossip_refund", ...);
    }
}
```

**攻击步骤**：悬赏帖到期后，并发请求任意触发 `refundExpired()` 的**只读**接口（`GET /api/gossip/posts`）。多线程同时读到同一条 `frozen` 记录 → 各自退款一次 → 悬赏被退 N 次。**攻击者无需写权限即可反复触发**。

**修复建议**：退款改条件更新 `UPDATE gossip_posts SET coin_status='refunded' WHERE id=? AND coin_status='frozen'`，`affectedRows==1` 才退款；且将惰性退款迁移为独立定时任务，读接口保持纯只读。

1. **短期**：将 JWT 有效期从 7 天缩短至 1–2 天；「记住我」仅保存邮箱，不保存令牌（要求重新登录）。
2. **中期**：改用 `HttpOnly + Secure + SameSite=Strict` Cookie 承载会话，使 JS 无法读取令牌。
3. **配套**：令牌绑定设备指纹/UA 哈希，异常环境失效。

### 6.2 越权（IDOR）防御 — 表现优异
以下接口**全部**做了正确的归属校验，未发现横向越权：

- `ClaimService`：`claim`（禁止认领自己任务）、`claimers`（仅发布者可见）、`pair`（仅发布者）、`submit`（按 `(taskId, claimerId)` 定位自己的认领）、`confirm`（仅发布者）、`cancel`（仅发布者）、`my-published`/`my-claimed`（仅本人）
- `GossipService`：`adopt`（仅发布者可采纳 + 校验回答归属帖子）、自问自答拦截、点赞唯一约束
- `ComplaintService`：修改吐槽校验 `userId.equals(c.getUserId())`、维度 key 白名单、metric 参数白名单
- `FeedbackService`：`read`/`follow-up` 均校验工单归属
- `RatingService`：**本项目校验最完整的模块** —— 校验评价者/被评价者均为参与者、方向符合 `RatePolicy`、任务已完成、窗口期内、`uk_rating` 防重复
- `NotificationService`：标记已读使用 `eq(id).eq(userId)` **双条件**，无法操作他人通知
- `CheckinService`：行锁 + `uk_user_date` 唯一键 + 捕获 `DuplicateKeyException` —— **本项目幂等实现最佳**

## 八、附录

### 8.1 审计方法论
1. **静态分析**：全量危险函数检索（`innerHTML`/`eval`/`${}` 拼接）+ 数据流追踪（source → sink）。
2. **威胁建模**：按资产（资金 / 账号 / 数据）+ 攻击面（前端 / API / 部署）+ 攻击者（外部 / 恶意用户 / 内部）三维度枚举。
3. **验证原则**：所有严重/高危结论均**由审计人亲自复核原始代码行**，不采信单一工具或代理输出。
4. **供应链核实**：联网核对 NVD / GitHub Advisory / Snyk / 厂商安全公告，区分真实 CVE 与网络误报。

### 8.3 总体风险判定

| 维度 | 评级 | 依据 |
|------|------|------|
| **当前可被实际利用的风险** | 🔴 **高** | H-01 铸币、X-01 XSS、B-02 口令硬编码——三者均已确认可实际触发 |
| **潜在风险（依赖生产配置）** | 🟠 **中高** | C-01、A-05、A-06 取决于运维配置 |
| **安全工程成熟度** | 🟡 **中** | 架构设计良好（鉴权/越权做得好），但**并发幂等**与**输出编码**两类基本功存在系统性缺口 |

**核心判断**：本项目的问题**不是设计能力不足**（权限模型与越权防御相当扎实），而是**两类工程纪律的缺失** —— ① 资金与计数类操作缺少「原子/条件更新」的统一约束；② 输出编码缺少「所有插值必须转义」的强制规范。建议将这两条写入 `PROJECT_RULES.md` 作为长期约束，其收益远超单点修复。
