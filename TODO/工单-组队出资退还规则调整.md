> **状态**: 待开发 | **创建日期**: 2026-09-15 | **优先级**: P0（资金安全）
> **涉及**: 后端 3 个文件 · 前端 1 个文件（约 14 处文案）· 文档 3 份

---

## 一、问题定性

### 1.1 需求目标（已与产品确认）

| # | 口径 | 确认结果 |
|---|------|---------|
| 1 | 要修的资金漏洞路径 | **审核驳回路径**（按 `reward` 退款导致凭空铸币） |
| 2 | 80% 退回的触发条件 | **改为「任务顺利完成」**，不再依赖「互评均分 ≥4」 |
| 3 | 冻结出资方式 | **保持现状**：发布者冻 10 + 每个被选中认领者各冻 10 |
| 4 | 退款时机 | **保留 3 天互评窗口**，由定时任务执行（仅去掉门槛，不动调度结构） |

### 1.2 核心缺陷：驳回退款口径与冻结口径不一致（凭空铸币）

**根因**：任务发布时的「冻结」是**按类型**判定的，而审核驳回时的「退款」是**无条件按 `reward`** 的，两者不对齐。

```java
// 发布：按类型冻结（TaskService.java:98-105）
if ("help".equals(dto.getTaskType())) {
    pointService.changeBalance(userId, -dto.getReward(), "freeze", ...);      // help 冻 reward
} else if ("team".equals(dto.getTaskType())) {
    pointService.changeBalance(userId, -TEAM_DEPOSIT, "freeze", ...);        // team 冻 10
}
// teach / reward 类型：完全不冻结
```

```java
// 驳回：无条件按 reward 退款（TaskService.java:239）—— ✗ 缺陷所在
pointService.changeBalance(task.getPublisherId(), task.getReward(), "refund",
        "任务审核驳回退回：" + task.getTitle(), taskId);
```

**受影响类型与铸币规模**：

| 任务类型 | 发布时实际冻结 | 驳回时实际退款 | 净增 | 是否可铸币 |
|---------|--------------|--------------|------|-----------|
| `help` 求助 | `reward` | `reward` | 0 | ✅ 正确 |
| `team` 组队 | **10** | `reward` | `reward − 10` | ❌ **铸币** |
| `teach` 教学 | **0** | `reward` | **`reward`** | ❌ **铸币（危害最直接）** |
| `reward` 官方 | **0** | `reward` | **`reward`** | ❌ 铸币（仅管理员可发） |

**攻击复现（teach 最易利用）**：
1. 前端发布教学任务时，`reward` 输入框是**用户可自由填写**的（仅 `@Min(1)`，无上限）；
2. 填写 `reward = 99999` → 系统**不冻结任何币**；
3. 管理员在审核中心点击「驳回」；
4. 账户凭空增加 **99999** 币。

> **注**：组队类型的 `reward` 被前端强制为 10（`growth-schoolv3.html:8635`），因此经 UI 无法触发组队铸币；但**直接调用 API 可绕过前端**，且后端无任何校验。故必须在后端修复。

### 1.3 次要问题：前端文案与实际逻辑不符

`growth-schoolv3.html:2817` 仍写「未及时互评按默认 4 分结算」，但后端已移除默认补分逻辑（`RatingService.java:371` 注释明确「不再补录默认评分」）。属历史遗留文案，一并修正。

### 变更 1（核心）· `TaskService.java` — 驳回退款改为按实际冻结额

#### 1.1 新增统一口径方法（放在 `TEAM_REFUND_RATIO` 常量定义之后，约第 52 行）

```java
/**
 * 任务发布时实际冻结的蛋蛋币金额（唯一的冻结口径来源）
 * 与 publish() 的冻结分支严格一一对应，禁止在其他地方重复推导
 * teach / reward 发布时不冻结 → 返回 0
 */
public static int frozenAmountOf(Task task) {
    if (task == null || task.getTaskType() == null) return 0;
    if ("help".equals(task.getTaskType())) {
        return task.getReward() == null ? 0 : task.getReward();
    }
    if ("team".equals(task.getTaskType())) {
        return TEAM_DEPOSIT;
    }
    return 0;   // teach / reward：无冻结
}
```

### 变更 2（核心）· `RatingService.java` — 去掉互评门槛 + 补幂等

**文件**：`backend/src/main/java/com/eggworld/service/RatingService.java`
**方法**：`settleTask(Long taskId)`（约第 375-411 行）

#### 2.1 需要新增的 Mapper 方法

**文件**：`backend/src/main/java/com/eggworld/mapper/TaskMapper.java`

```java
/**
 * 幂等抢占结算权：仅当 settled=0 时置为 1
 * @return 影响行数（1=抢到，0=已被其他线程结算）
 */
@Update("UPDATE tasks SET settled = 1 WHERE id = #{taskId} AND settled = 0")
int markSettled(@Param("taskId") Long taskId);
```

> 需引入 `org.apache.ibatis.annotations.Update` 与 `@Param`。

#### 2.2 改写后完整方法

```java
/**
 * 组队任务结算（互评期到期后由定时任务调用，或任务完成即已具备条件）：
 * 1. 资金：任务「顺利完成」（status=completed）即退还 80% 出资，与互评结果无关
 * 2. 口碑：互评结果仍写入 ratings 表参与口碑计算，但不再影响出资退还
 * 3. 幂等：以 settled 条件抢占保证只结算一次
 */
@Transactional
public void settleTask(Long taskId) {
    Task task = taskMapper.selectById(taskId);
    if (task == null || !"team".equals(task.getTaskType())
            || !"completed".equals(task.getStatus())
            || (task.getSettled() != null && task.getSettled() == 1)) {
        return; // 状态不符或已结算，跳过
    }

    // ★ 先抢占结算权（条件更新），抢不到说明已被并发结算，直接返回
    int won = taskMapper.markSettled(taskId);
    if (won != 1) {
        return;
    }

    // 参与者：发布者 + 被选中认领者
    List<Long> participants = new ArrayList<>();
    participants.add(task.getPublisherId());
    taskClaimMapper.selectList(new LambdaQueryWrapper<TaskClaim>()
                    .eq(TaskClaim::getTaskId, taskId)
                    .eq(TaskClaim::getSelected, 1))
            .forEach(c -> participants.add(c.getClaimerId()));

    // 无条件退还 80% 出资（原「互评均分≥4」门槛已移除）
    int refund = (int) Math.round(TaskService.TEAM_DEPOSIT * TaskService.TEAM_REFUND_RATIO);
    for (Long pid : participants) {
        pointService.changeBalance(pid, refund, "refund",
                "组队任务完成，退还 80% 出资：" + task.getTitle(), taskId);
        notificationService.notify(pid,
                "你在「" + task.getTitle() + "」的组队任务已完成，已退还 " + refund
                        + " 蛋蛋币（出资 " + TaskService.TEAM_DEPOSIT + " 币的 80%）", "settle");
    }
}
```

**要点说明**：
- ✅ 移除了 `BigDecimal avg = ratingMapper.avgByRateeInTask(...)` 及其 `if (avg >= 4)` 判断，`else` 分支（"出资不退还"）一并删除；
- ✅ 将 `task.setSettled(1)` 从**方法末尾**提前到**发钱之前**，并改为条件更新 —— 修复并发下重复退款（原实现存在「先发钱、后置标记」的竞态窗口）；
- ⚠️ 若 `BigDecimal` 与 `ratingMapper` 在本方法中已无其他引用，可移除对应 import（保留不影响编译）。

## 四、存量数据兼容性（重要：无需迁移）

| 场景 | 处理 |
|------|------|
| 已 `completed` 且 `settled=0` 的组队任务 | 仍由 `RateSettleScheduler` 按**新逻辑**处理 → **无条件退 80%**（比旧逻辑更宽松，不会出现资金卡死） |
| 已 `settled=1` 的任务 | 直接跳过，不受影响 |
| 已 `rejected` 的历史任务 | 已退款完成，**不做回溯修正**（如需追回异常退款，需单独出数据核对工单） |
| `rate_deadline` 字段 | 保留不变，继续作为互评窗口的时间依据 |

**结论**：本次变更**向后兼容**，无需数据库迁移脚本；新逻辑对用户更宽松，不存在存量用户被"卡住资金"的情况。
